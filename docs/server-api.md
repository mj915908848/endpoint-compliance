# Server API v1

JSON uses camelCase and string enums from `Compliance.Core.Wire`. All endpoints return JSON except `.md`; errors are `{error:string}`. Frontend receives no sample devices. Lists are bare arrays. `/api/status` exposes mode, storage provider, network capabilities and signing public key (no secrets).

Login POST `/api/auth/login` `{username,password}` returns `{username,roles:string[],csrfToken}` and an HttpOnly SameSite=Strict 8-hour cookie. `/api/me` returns same shape. All subsequent management writes require `X-CSRF-Token`. Logout POST `/api/auth/logout`. No built-in account or password; bootstrap supplied via environment. Roles: Reader reads; Operator acknowledges and requests scans/registration codes; Publisher creates/publishes drafts; Reviewer approves a different publisher's draft. Every mutation is audited.

Devices GET `/api/devices` -> `DeviceSummary[]` from Core; GET `/api/devices/{id}` -> `{device:DeviceSummary,snapshot:ScanSnapshot|null,controls:ControlState[],pendingCommands:number}`. GET `/api/devices/{id}/report` -> `ComplianceReport` (404 before first scan); `.md` -> Markdown. GET `/api/alerts` -> `AlertSummary[]`; POST `/api/alerts/{id}/ack` -> `{ok:true}`; acknowledgment does not resolve technical state. GET `/api/audit` -> `{id,actor,action,target,at}[]`.

POST `/api/enrollment-codes` `{expiresMinutes?:number}` -> `{code,expiresAt}`. Code shown once, stored as hash. POST `/api/devices/{id}/commands` `{type:"ScanNow"}` -> `DeviceCommand`. Arbitrary commands rejected. GET `/api/policies/current` -> `SignedPolicy`. GET `/api/policies/drafts` -> `{id,document:PolicyDocument,createdBy,approvedBy:string|null,published:bool}[]`. POST same path `{document:PolicyDocument,impactReviewed:bool}` -> draft. POST `/api/policies/{id}/approve` `{}` -> draft; POST `/api/policies/{id}/publish` `{}` -> `SignedPolicy`. Separate reviewer required; explicit target devices and verified controls required for enforcement. Seed current policy is Audit, immutable signed version 1.

Agent endpoints use Core contracts: unauthenticated POST `/api/agent/enroll` EnrollmentRequest -> EnrollmentResponse; then POST heartbeat HeartbeatRequest, GET policy SignedPolicy, POST events EventBatch -> EventReceipt, GET commands DeviceCommand[], POST `/api/agent/commands/{id}/ack` CommandReply. Signed headers X-Device-Id, X-Timestamp (Unix seconds), X-Nonce (UUID), X-Signature. Canonical signature uses exact body bytes, method uppercase and path without query (Core RequestAuthentication); 5-minute clock window; nonces persisted. Enrollment uses one-time expiring code and distinct ECDSA public key.

Event types `Snapshot`, `Violation`, `Recovered`, `Health`, `BlockedAttempt` use persistent sequence >0, immutable event id, source time, object key; Snapshot includes snapshot. Violation/Recovered current incidents advance only on higher sequence per object. Snapshot current selection uses original collection time (and sequence for ties), never arrival time. Source times over 5 minutes in the future are rejected. Event ids and sequences must never be reused with different content. Offline uses server receipt of authenticated heartbeat: SuspectedOffline 3 minutes, Offline 5 minutes. Current verdict UNKNOWN when offline; last verdict remains visible. Historical stale snapshots cannot claim fresh PASS.

Production uses PostgreSQL and HTTPS. Explicit `Compliance:DemoMode=true`, `Compliance:Storage=Sqlite` requires loopback requests/listener; HTTP permitted only there. Forwarded headers require configured trusted proxy IP(s); never trust arbitrary X-Forwarded-Proto. Deployment configuration details follow in README/deploy documentation.

## Configuration and deployment boundary

- Environment variables map using `__`: `Compliance__Storage=Postgres`, `Compliance__Database=<Npgsql connection string>`, `Compliance__SigningKeyPath=/protected/policy-signing.pem`, `Compliance__BootstrapUsers=<JSON array>`. Use protected secret injection, not command-line passwords. Bootstrap creates absent accounts only; existing passwords/roles are never overwritten. Passwords require at least 16 characters and PBKDF2-SHA256 salts. An empty bootstrap leaves no login account; no default secret exists.
- First startup creates a P-256 signing PEM in the configured path (owner-only Unix mode); retain and back up this key alongside the database. A key inconsistent with stored releases rejects startup. On Windows deployment, the service account directory ACL must protect this key. One server signing identity per customer instance; key rotation is not yet implemented.
- Explicit demo: `Compliance__DemoMode=true`, `Compliance__Storage=Sqlite`, `Compliance__Database=/local/data/compliance.db`, `ASPNETCORE_URLS=http://127.0.0.1:5080`. By default both listener and request source must be loopback. For isolated LAN trials only, set `Compliance__DemoHttpLan=true` and bind `ASPNETCORE_URLS` to an explicit private IPv4 address; private IPv4 client sources are then accepted. HTTP carries credentials and reports in cleartext. Do not expose the trial listener to public networks or treat this as production deployment.
- Production requires HTTPS on every request. Terminating TLS at a customer reverse proxy is supported only with `Compliance__TrustedProxies__0=<exact proxy IP>` and subsequent numbered entries. Forward limit is one hop; unknown proxies cannot assert HTTPS through a header. Configure the reverse proxy to replace forwarded headers, limit uploads to 2 MiB, and restrict the application listener to the proxy; deploy PostgreSQL access using a service-specific account and verified TLS. No public CORS is enabled.
- `Reader` must be included for management read access; permission to edit does not implicitly add read permission. Publishers and reviewers must be different both from draft author and publishing actor. Seed bootstrap can create separately named users for these roles.
- Build UI before server publish. `ui/dist` is copied to the dev server's ignored `wwwroot` and included as `wwwroot` content in the published output. Static client assets use only same-origin API; login/write requests must preserve cookies and CSRF header.

## Persistence and operational limitations

All state uses a transactional `records(kind,id,json)` table with composite primary key. PostgreSQL transactions take a shared advisory lock across instances for event deduplication, sequence ownership, snapshot selection, enrollment redemption, command replies and policy publishing. SQLite uses a file-backed transaction plus single-process serialization; do not run multiple demo processes on the same file. Events retain original source times and a separate server receipt time; SHA-256 fingerprints allow immutable raw-input deduplication while snapshots, summaries and event payloads are sanitized before persistence. No raw request body, enrollment token or password is recorded in audit.

Device policy assignments reference immutable release versions. A targeted release does not change other devices' assignment. Snapshot-derived incidents aggregate by product and SID (proxy objects remain distinct); direct event incidents update by object key and persistent sequence. Only newest non-stale snapshot state can open/resolve snapshot incidents. Recovery requires no coverage gaps and fresh Complete modules for the incident's original scope; it does not follow acknowledgment. Offline transition polling runs every 15 seconds and also on device/alert reads. Authenticated heartbeat source time must be within five minutes; receipt time determines reachability, never scan freshness.

This build records notifications in the management alert center only; SMTP/external delivery, retention pruning, account administration/password resets, directory identity, key rotation, policy rollback orchestration and backup/PITR automation remain deployment follow-up work. Preserve database and signing-key backups; perform a real restore test before production rollout. Capacity/load goals have not been measured. Application and browser policy publishing is capability-gated; the generic network adapter is absent and its requested enforcement release is always rejected. No endpoint runs a remote shell, uninstall or arbitrary update payload.

## Verification

`dotnet test tests/Compliance.Server.Tests` uses real durable SQLite files and ASP.NET TestServer. Set `COMPLIANCE_TEST_POSTGRES` to a loopback test-database connection string to run the same suite on PostgreSQL; tests create generated isolated schemas and drop only their own schemas. Tests cover enrollment expiry/reuse/restart, authenticated nonce replay and signature path/body binding, atomic batch rollback, duplicate and sequence conflict handling, out-of-order recovery, old scan freshness, offline current reports, RBAC/CSRF, separate review and immutable publishing, per-device policy targeting, sanitization, snapshot alert recovery and scoped fixed commands. Actual proxy TLS and native Windows controls require separate deployment acceptance.
