# Server API v1

JSON uses camelCase and string enums from `Compliance.Core.Wire`. Signed-in administrators can read the OpenAPI 3.1 document of every endpoint at GET `/api/openapi.json`; `ui/openapi.json` is a copy of it, kept equal by a server test (regenerate with `UPDATE_OPENAPI=1 dotnet test tests/Compliance.Server.Tests --filter OpenApiTests`), and the UI's types in `ui/src/api.gen.ts` are generated from that copy with `npm run api`, which CI checks. All endpoints return JSON except `.md`; errors are `{error:string}`. Frontend receives no sample devices. Lists are bare arrays. `/api/status` exposes the release version, mode, storage provider, network capabilities and signing public key (no secrets).

Login POST `/api/auth/login` `{username,password}` returns `{username,roles:string[],csrfToken,idleMinutes}` and an HttpOnly SameSite=Strict 8-hour cookie. `/api/me` returns same shape. A session also ends after `SessionIdleMinutes` (default 30, 0 turns it off) without use; requests may send `X-Idle-Seconds` (how long since the administrator last typed or clicked, which the UI sends with its polling), and requests without it count as use. Path checks for authentication ignore case, as routing does. All subsequent management writes require `X-CSRF-Token`. Logout POST `/api/auth/logout`. No built-in account or password; bootstrap supplied via environment. Roles: Reader reads; Operator acknowledges and requests scans/registration codes; Publisher edits and publishes policies; Reviewer is still accepted in bootstrap configuration but grants nothing. Every mutation is audited.

Devices GET `/api/devices` -> `DeviceSummary[]` from Core; GET `/api/devices/{id}` -> `{device:DeviceSummary,snapshot:ScanSnapshot|null,controls:ControlState[],pendingCommands:number}`. GET `/api/devices/{id}/report` -> `ComplianceReport` (404 before first scan); `.md` -> Markdown. GET `/api/devices/{id}/history?days=1..400` (default 90) -> `{deviceId,at,verdict,violationCount,policyVersion}[]`, the device's verdict changes oldest first. GET `/api/devices/trend?days=1..90&offset=<minutes east of UTC>` (default 30 days, UTC) -> `{date,pass,fail,unknown}[]`, one per day ending today in that time zone: enrolled devices counted by their stored verdict at the end of the day (today: now), whether online or not. GET `/api/alerts` -> `AlertSummary[]`: alerts not resolved and those resolved in the last 30 days, newest first; GET `/api/alerts/resolved?before=<time>&beforeId=<id>&limit=1..500` (default 100) -> the next page of older resolved alerts, newest first, starting after the last one shown. Resolved alerts are deleted `AlertRetentionDays` (default 180) after they resolved; POST `/api/alerts/{id}/ack` -> `{ok:true}`; acknowledgment does not resolve technical state. GET `/api/audit` -> `{id,actor,action,target,at}[]`.

POST `/api/enrollment-codes` `{expiresMinutes?:1..10080, maxUses?:1..500, label?}` (Operator) -> `{code,id,label,expiresAt,maxUses}`; defaults 15 minutes and one device. The code is shown once and stored as a hash; it enrolls devices until `maxUses` is reached, it expires or it is revoked. GET `/api/enrollment-codes` (Operator) -> the 100 newest codes `[{id,label,expiresAt,maxUses,uses,createdAt,createdBy,revoked}]`; DELETE `/api/enrollment-codes/{id}` (Operator) revokes one. POST `/api/devices/{id}/commands` `{type:"ScanNow"}` -> `DeviceCommand`. Arbitrary commands rejected. Policies: the default policy (key `default`, named "Default") applies to every device that no named policy lists; a named policy applies to the devices in its `targetDeviceIds`, and a device can be in at most one named policy. Versions come from one sequence shared by all policies. GET `/api/policies` -> `[{key,isDefault,release:SignedPolicy,devices}]`, default first. GET `/api/policies/current` -> the default policy's `SignedPolicy`. GET `/api/policies/template` -> the built-in `PolicyDocument` of this server version. POST `/api/policies/{key}` `PolicyDocument` (Publisher) -> `{key,isDefault,release,devices}` publishes a new release in one step (`new` creates a policy); the server sets `version` to the newest version + 1, `issuedAt` to now and `expiresAt` to one year later, and rejects invalid content, duplicate names and devices already in another named policy with a Chinese message. With `?baseVersion=<version>` (the release the edit started from; the UI always sends it) it returns 409 when the policy has had a newer release since, so an edit never silently replaces someone else's. POST `/api/policies` publishes the default policy and returns its `SignedPolicy`. DELETE `/api/policies/{key}` (Publisher) deletes a named policy; its devices return to the default policy. Agents refuse a lower version than they hold, so when devices move to a policy whose newest release is older, the server re-issues it under a new version (audited as `ReissuePolicy`). The default policy is Audit only; enforcement needs a named policy with explicit target devices and verified controls. Seed policy is Audit, immutable signed version 1; a default policy still carrying an earlier built-in name is re-issued as "Default" at startup. DELETE `/api/devices/{id}` (Operator) removes a device and its events, alerts and commands; its agent must re-enroll.

Agent endpoints use Core contracts: unauthenticated POST `/api/agent/enroll` EnrollmentRequest -> EnrollmentResponse; then POST heartbeat HeartbeatRequest, GET policy SignedPolicy, POST events EventBatch -> EventReceipt, GET commands DeviceCommand[], POST `/api/agent/commands/{id}/ack` CommandReply. Signed headers X-Device-Id, X-Timestamp (Unix seconds), X-Nonce (UUID), X-Signature. Canonical signature uses exact body bytes, method uppercase and path without query (Core RequestAuthentication); 5-minute clock window; nonces persisted. Enrollment uses one-time expiring code and distinct ECDSA public key.

Event types `Snapshot`, `Violation`, `Recovered`, `Health`, `BlockedAttempt` use persistent sequence >0, immutable event id, source time, object key; Snapshot includes snapshot. Violation/Recovered current incidents advance only on higher sequence per object. Snapshot current selection uses original collection time (and sequence for ties), never arrival time. Source times over 5 minutes in the future are rejected. Event ids and sequences must never be reused with different content. Offline uses server receipt of authenticated heartbeat: SuspectedOffline 3 minutes, Offline 5 minutes. Current verdict UNKNOWN when offline; last verdict remains visible. Historical stale snapshots cannot claim fresh PASS.

Production uses PostgreSQL and HTTPS. Explicit `Compliance:DemoMode=true`, `Compliance:Storage=Sqlite` requires loopback requests/listener; HTTP permitted only there. Forwarded headers require configured trusted proxy IP(s); never trust arbitrary X-Forwarded-Proto. Deployment configuration details follow in README/deploy documentation.

## Configuration and deployment boundary

- Environment variables map using `__`: `Compliance__Storage=Postgres`, `Compliance__Database=<Npgsql connection string>`, `Compliance__SigningKeyPath=/protected/policy-signing.pem`, `Compliance__BootstrapUsers=<JSON array>`. Use protected secret injection, not command-line passwords. Bootstrap creates absent accounts only; existing passwords/roles are never overwritten. Passwords require at least 16 characters and PBKDF2-SHA256 salts. An empty bootstrap leaves no login account; no default secret exists.
- First startup creates a P-256 signing PEM in the configured path (owner-only Unix mode); retain and back up this key alongside the database. A key inconsistent with stored releases rejects startup. On Windows deployment, the service account directory ACL must protect this key. One server signing identity per customer instance; key rotation is not yet implemented.
- Explicit demo: `Compliance__DemoMode=true`, `Compliance__Storage=Sqlite`, `Compliance__Database=/local/data/compliance.db`, `ASPNETCORE_URLS=http://127.0.0.1:5080`. By default both listener and request source must be loopback. For isolated LAN trials only, set `Compliance__DemoHttpLan=true` and bind `ASPNETCORE_URLS` to an explicit private IPv4 address; private IPv4 client sources are then accepted. HTTP carries credentials and reports in cleartext. Do not expose the trial listener to public networks or treat this as production deployment.
- Production requires HTTPS on every request. Terminating TLS at a customer reverse proxy is supported only with `Compliance__TrustedProxies__0=<exact proxy IP>` and subsequent numbered entries. Forward limit is one hop; unknown proxies cannot assert HTTPS through a header. Configure the reverse proxy to replace forwarded headers, limit uploads to 2 MiB, and restrict the application listener to the proxy; deploy PostgreSQL access using a service-specific account and verified TLS. No public CORS is enabled.
- `Reader` must be included for management read access; permission to edit does not implicitly add read permission. Policy publishing is a single Publisher action, recorded in the audit log.
- Build UI before server publish. `ui/dist` is copied to the dev server's ignored `wwwroot` and included as `wwwroot` content in the published output. Static client assets use only same-origin API; login/write requests must preserve cookies and CSRF header.

## Persistence and operational limitations

State lives in typed tables created by ordered migrations in `src/Compliance.Server/Storage/Migrations.cs` (`schema_migrations` records applied versions; startup applies missing ones in one transaction under an advisory lock). Tables: `users`, `sessions`, `enrollment_codes`, `devices`, `events` (primary key `(device_id,event_id)`, unique `(device_id,sequence)`), `alerts`, `snapshot_incidents`, `policy_releases` (immutable; the current policy is the newest release), `policy_drafts`, `commands`, `audit`, `nonces`, `verdict_history`. Each device row also stores its verdict as last evaluated (`verdict`, `violation_count`, `verdict_valid_until`, `verdict_sequence`, `verdict_policy`, `verdict_detail`): written when a snapshot arrives and by a background refresh every 15 seconds for devices whose snapshot, policy or validity no longer matches it; lists read it and only evaluate, without storing, devices whose stored verdict no longer holds. Every change of a stored verdict adds a `verdict_history` row; rows older than 400 days are pruned except each device's latest. Times are stored as UTC ticks (BIGINT); only free-form documents (snapshots, controls, policy payloads, sanitized event bodies) are JSON text. A 0.1.0 database is imported once from `records(kind,id,json)`, which is then kept as `records_legacy_v0` for inspection or rollback. PostgreSQL transactions run concurrently and serialize only where they share state through transaction-scoped advisory locks: per device (heartbeat, event batches, command replies, alert acknowledgment), policy review/publishing, enrollment redemption, offline-state transitions and migrations. SQLite uses a file-backed transaction plus single-process serialization; do not run multiple demo processes on the same file. Events retain original source times and a separate server receipt time; SHA-256 fingerprints allow immutable raw-input deduplication while snapshots, summaries and event payloads are sanitized before persistence. No raw request body, enrollment token or password is recorded in audit.

Device policy assignments reference immutable release versions. A targeted release does not change other devices' assignment. Snapshot-derived incidents aggregate by product and SID (proxy objects remain distinct); direct event incidents update by object key and persistent sequence. Only newest non-stale snapshot state can open/resolve snapshot incidents. Sensitive file evidence (`kind:SensitiveFile`, module `sensitive-files`, scopes are user SIDs or `drive:<letter>`) opens one alert per reported path: type `SensitiveFile` for rules with `action:"Alert"` (the default; no effect on the verdict) and `Violation` for `action:"Violation"`. Such an alert resolves only when a fresh `Complete` scan of its scope no longer lists the path, or when scanning is disabled; `Truncated` or failed scans prove nothing. Recovery requires no coverage gaps and fresh Complete modules for the incident's original scope; it does not follow acknowledgment. Offline transition polling runs every 15 seconds in the background; device and alert reads do not write. Authenticated heartbeat source time must be within five minutes; receipt time determines reachability, never scan freshness.

This build records notifications in the management alert center only; SMTP/external delivery, retention pruning, account administration/password resets, directory identity, key rotation, policy rollback orchestration and backup/PITR automation remain deployment follow-up work. Preserve database and signing-key backups; perform a real restore test before production rollout. Capacity/load goals have not been measured. Application and browser policy publishing is capability-gated; the generic network adapter is absent and its requested enforcement release is always rejected. No endpoint runs a remote shell, uninstall or arbitrary update payload.

## Verification

`dotnet test tests/Compliance.Server.Tests` uses real durable SQLite files and ASP.NET TestServer. Set `COMPLIANCE_TEST_POSTGRES` to a loopback test-database connection string to run the same suite on PostgreSQL; tests create generated isolated schemas and drop only their own schemas. Tests cover enrollment expiry/reuse/restart, authenticated nonce replay and signature path/body binding, atomic batch rollback, duplicate and sequence conflict handling, out-of-order recovery, old scan freshness, offline current reports, RBAC/CSRF, separate review and immutable publishing, per-device policy targeting, sanitization, snapshot alert recovery and scoped fixed commands. Actual proxy TLS and native Windows controls require separate deployment acceptance.
