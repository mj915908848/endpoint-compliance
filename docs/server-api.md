# Server API v1

JSON uses camelCase and string enums from `Compliance.Core.Wire`. Signed-in administrators can read the OpenAPI 3.1 document of every endpoint at GET `/api/openapi.json`; `ui/openapi.json` is a copy of it, kept equal by a server test (regenerate with `UPDATE_OPENAPI=1 dotnet test tests/Compliance.Server.Tests --filter OpenApiTests`), and the UI's types in `ui/src/api.gen.ts` are generated from that copy with `npm run api`, which CI checks. All endpoints return JSON except `.md`; errors are `{error:string}`. Frontend receives no sample devices. Lists are bare arrays. `/api/status` exposes the release version, mode, storage provider, network capabilities and signing public key (no secrets).

Login POST `/api/auth/login` `{username,password,code?}` returns `{username,roles:string[],csrfToken,idleMinutes,twoFactor,twoFactorRequired}` and an HttpOnly SameSite=Strict 8-hour cookie. `/api/me` returns same shape. A session also ends after `SessionIdleMinutes` (default 30, 0 turns it off) without use; requests may send `X-Idle-Seconds` (how long since the administrator last typed or clicked, which the UI sends with its polling), and requests without it count as use. Path checks for authentication ignore case, as routing does. All subsequent management writes require `X-CSRF-Token`. Logout POST `/api/auth/logout`. No built-in account or password; bootstrap supplied via environment. Roles: Reader reads; Operator acknowledges and requests scans/registration codes; Publisher edits and publishes policies; Admin manages accounts; Reviewer is still accepted in bootstrap configuration but grants nothing. Bootstrap accounts holding Operator and Publisher also get Admin, and so did such accounts when migration 19 ran. Every mutation is audited.

Two-step sign-in (TOTP, RFC 6238: HMAC-SHA1, 30-second steps, 6 digits, one step of drift either way, each step accepted once). For an account that has it, a right password without `code` answers 401 `{error:"TwoFactorRequired"}`; a wrong code is 401, counts towards the login throttle and is audited `LoginWrongCode`. Wrong passwords answer `Invalid credentials` whether or not the account has it, and so do disabled accounts. POST `/api/auth/two-factor/setup` `{}` -> `{secret,uri}` (Base32 secret and otpauth:// URI for a QR code) stores a pending secret; POST `/api/auth/two-factor/enable` `{code}` turns it on once a code from it is right (`EnableTwoFactor`); POST `/api/auth/two-factor/disable` `{password,code}` turns it off (`DisableTwoFactor`), refused while it is required. PUT `/api/settings/require-two-factor` `{required}` (Admin, who must have it on first; `SetRequireTwoFactor`): while required, a session of an account without it may only call `/api/me`, `/api/auth/logout`, `/api/auth/password` and the setup and enable calls; anything else is 403.

Asset inventory: agents POST `/api/agent/inventory` (signed like other agent calls) with `{collectedAt,hardware:{manufacturer,model,serialNumber,biosVersion,processor,cores,logicalProcessors,memoryBytes},operatingSystem:{name,version,displayVersion,architecture,installedAt,lastBootAt},disks:[{model,sizeBytes,mediaType,busType}],volumes:[{name,label,fileSystem,sizeBytes,freeBytes}],software:[{name,version,publisher,installedOn,scope}]}` (at most 5000 programs and 64 disks/volumes; `scope` is `machine` or the account) after a full check when it changed, and at least daily; one collected before the stored one is ignored. Each later inventory records its differences (`SoftwareInstalled`, `SoftwareRemoved`, `SoftwareUpdated`, `SystemUpdated`, `HardwareChanged`; at most 300 per inventory) in `inventory_changes` (migration 21, kept 365 days). Readers: GET `/api/devices/{id}/inventory` -> `{inventory|null,receivedAt,changes}`; GET `/api/assets` -> hardware of each device in use; GET `/api/assets/software` -> `[{name,publisher,devices,versions:[{version,devices}]}]`; GET `/api/assets/software/devices?name=` -> `[{deviceId,hostName,note,group,version,scope,installedOn}]`; GET `/api/assets/changes?days=30` (1..365, newest 1000); GET `/api/assets/export.csv` (`ExportAssets`) and `/api/assets/software/export.csv` (`ExportSoftware`).

Log forwarding (Admin): GET `/api/settings/log-forwarding` -> `{settings:{enabled,host,port,protocol:"Udp"|"Tcp"|"Tls",format:"Json"|"Cef",facility:16..23,alerts,audit,caCertificate},last:{at,ok,error,sent}|null}`; PUT the same `settings` (`SetLogForwarding`; host trimmed, required when enabled; `caCertificate` PEM, optional, trusted for Tls besides the system store); POST `/api/settings/log-forwarding/test` -> `{ok,error}` sends one message with the saved settings (`TestLogForwarding`). Every 10 seconds the server sends, oldest first, alerts that were raised, raised again or resolved since they were last sent (`alerts.forwarded_state`/`forwarded_activation`, migration 20) and audit records after the saved cursor (setting `log-forwarding-audit`; records younger than 5 seconds wait for the next run). Messages are RFC 5424 (`<PRI>1 time host endpoint-compliance - alert|audit - MSG`); MSG is JSON (`{kind:"alert",event:"raised"|"resolved",id,type,typeName,severity,deviceId,hostName,deviceNote,summary,firstSeen,lastSeen,acknowledged}` or `{kind:"audit",id,at,actor,action,target}`) or CEF (`CEF:0|恺域科技|终端合规管控|<version>|alert:<type>|audit:<action>|<name>|<severity>|rt=… dhost=… msg=… act=… externalId=… cs1..cs3` / `suser=…`). Tcp ends each message with LF; Tls (RFC 5425) uses octet counting. A failed send is retried next run; while forwarding or a kind is off, its records are passed over, and so is everything before forwarding is first set up.

Accounts (Admin): GET `/api/users` -> `{users:[{username,roles,twoFactor,disabled,lastLoginAt}],requireTwoFactor}`. POST `/api/users` `{username,password,roles}` creates one (name trimmed, 1 to 100 characters; password at least 12; 409 if it exists; `CreateUser`). PUT `/api/users/{username}/roles` `{roles}` (`SetUserRoles`). POST `/api/users/{username}/password` `{password}` -> `{signedOut}` resets another account's password and ends its sessions (`ResetUserPassword`). POST `/api/users/{username}/disable` and `/enable` (`DisableUser`, `EnableUser`): a disabled account cannot sign in and its sessions end; it is kept, so bootstrap does not create it again. DELETE `/api/users/{username}/two-factor` turns another account's two-step sign-in off and ends its sessions (`ResetTwoFactor`). An administrator cannot disable, reset the password or two-step sign-in of their own account here, and no change may leave no enabled account with Admin.

Devices GET `/api/devices` -> `DeviceSummary[]` from Core, the devices in use; `?archived=true` lists the archived ones instead (`archivedAt` set). GET `/api/devices/{id}` -> `{device:DeviceSummary,snapshot:ScanSnapshot|null,controls:ControlState[],pendingCommands:number,health:ClientHealth|null,healthProblems:string[]}`, `health` being what the client last reported about itself. POST `/api/devices/archive`, `/api/devices/restore` and `/api/devices/delete` `{ids:[...]}` (Operator, 1 to 1000 ids) -> `{done}` archive, restore or delete several devices at once. POST `/api/devices/group` `{ids:[...],group}` (Operator, 1 to 1000 ids) -> `{done}` puts the devices in a group (`DeviceSummary.group`, trimmed, at most 64 characters, compared case-insensitively) or, with an empty group, takes them out; it is audited as `SetDeviceGroup` and the devices are reassigned to the policy their group now selects. Archived devices are left out of the device list, overview counts, trend, CSV export, policy device counts, client upgrades and the signing-key rotation's waiting list; archiving resolves their alerts and they get no offline alerts. A heartbeat from an archived device restores it (audited `RestoreDevice` by `system`). Maintenance archives devices whose last heartbeat is older than the days chosen with PUT `/api/settings/archive-days` `{days:0|30|60|90|180}` (Operator; default 30, 0 never), returned as `archiveDays` by GET `/api/settings`. GET `/api/devices/{id}/report` -> `ComplianceReport` (404 before first scan); `.md` -> Markdown. GET `/api/devices/{id}/history?days=1..400` (default 90) -> `{deviceId,at,verdict,violationCount,policyVersion}[]`, the device's verdict changes oldest first. GET `/api/devices/trend?days=1..90&offset=<minutes east of UTC>` (default 30 days, UTC) -> `{date,pass,fail,unknown}[]`, one per day ending today in that time zone: enrolled devices counted by their stored verdict at the end of the day (today: now), whether online or not. GET `/api/alerts` -> `AlertSummary[]`: alerts not resolved and those resolved in the last 30 days, newest first; GET `/api/alerts/resolved?before=<time>&beforeId=<id>&limit=1..500` (default 100) -> the next page of older resolved alerts, newest first, starting after the last one shown. Resolved alerts are deleted `AlertRetentionDays` (default 180) after they resolved; POST `/api/alerts/{id}/ack` -> `{ok:true}`; acknowledgment does not resolve technical state. GET `/api/audit` -> `{id,actor,action,target,at}[]`.

POST `/api/enrollment-codes` `{expiresMinutes?:1..10080, maxUses?:1..500, label?, group?}` (Operator) -> `{code,id,label,expiresAt,maxUses,group}`; defaults 15 minutes and one device. The code is shown once and stored as a hash; it enrolls devices until `maxUses` is reached, it expires or it is revoked. GET `/api/enrollment-codes` (Operator) -> the 100 newest codes `[{id,label,expiresAt,maxUses,uses,createdAt,createdBy,revoked,group}]`; devices enrolled with a code that has a group join that group; DELETE `/api/enrollment-codes/{id}` (Operator) revokes one. POST `/api/devices/{id}/commands` `{type:"ScanNow"}` -> `DeviceCommand`. Arbitrary commands rejected. Policies: the default policy (key `default`, named "Default") applies to every device that no named policy lists; a named policy applies to the devices in its `targetDeviceIds` or, instead, to the devices whose group is in its `targetGroups` (not both, and not in Enforce mode); a device can be listed by at most one named policy and a group used by at most one, and a device listed by id takes that policy over its group's. Versions come from one sequence shared by all policies. GET `/api/policies` -> `[{key,isDefault,release:SignedPolicy,devices}]`, default first. GET `/api/policies/current` -> the default policy's `SignedPolicy`. GET `/api/policies/template` -> the built-in `PolicyDocument` of this server version. POST `/api/policies/{key}` `PolicyDocument` (Publisher) -> `{key,isDefault,release,devices}` publishes a new release in one step (`new` creates a policy); the server sets `version` to the newest version + 1, `issuedAt` to now and `expiresAt` to one year later, and rejects invalid content, duplicate names and devices or groups already in another named policy with a Chinese message (409 for a group). With `?baseVersion=<version>` (the release the edit started from; the UI always sends it) it returns 409 when the policy has had a newer release since, so an edit never silently replaces someone else's. POST `/api/policies` publishes the default policy and returns its `SignedPolicy`. DELETE `/api/policies/{key}` (Publisher) deletes a named policy; its devices return to the default policy. Agents refuse a lower version than they hold, so when devices move to a policy whose newest release is older, the server re-issues it under a new version (audited as `ReissuePolicy`). The default policy is Audit only; enforcement needs a named policy with explicit target devices and verified controls. Seed policy is Audit, immutable signed version 1; a default policy still carrying an earlier built-in name is re-issued as "Default" at startup. DELETE `/api/devices/{id}` (Operator) removes a device and its events, alerts and commands; its agent must re-enroll.

Client packages (remote upgrade): GET `/api/client-packages` (Reader) -> `[{version,sha256,size,uploadedAt,uploadedBy,outdated}]`, newest first, `outdated` counting devices whose client is older. POST `/api/client-packages?version=<x.y.z>` (Publisher) with the MSI as the `application/octet-stream` body stores the file under `PackageDirectory` (default `client-packages` next to the signing key) named by its SHA-256, and signs `{version,sha256,size,uploadedAt}` with the policy signing key over `"compliance-client-package\n" + payload`, so a package signature never verifies as a policy; files that do not start with the MSI header are refused, an existing version is 409. DELETE `/api/client-packages/{version}` (Publisher). POST `/api/client-packages/{version}/rollout?count=<n>` (Operator) -> `{queued}` sends an `Upgrade` command to every device in use whose client is older and has no upgrade pending or installing, or with `count` to that many first, online and most recently seen ones before others; failed and expired upgrades are sent again. GET `/api/client-packages/{version}/rollout` (Reader) -> `{version,devices:[{deviceId,hostName,note,onlineState,agentVersion,state,detail,sentAt}],remaining}`, the latest upgrade to that version per device, `state` being `Waiting`, `Installing`, `Succeeded` (the client reports that version or said so), `Failed` (download, check or installer failed), `NotApplied` (started over an hour ago, no outcome, still older) or `Expired`; `remaining` counts outdated devices not sent it yet; POST `/api/devices/{id}/commands` `{type:"Upgrade",version?}` (Operator) sends one, to the newest package when `version` is left out. Upgrade commands carry `version` and expire after one day. The agent fetches GET `/api/agent/client-packages/{version}` (`SignedClientPackage`), verifies it with the policy key it pinned at enrollment, refuses versions not newer than itself, downloads GET `/api/agent/client-packages/{version}/file` into its protected data directory, checks size, MSI header and SHA-256, replies, then records the upgrade in `upgrade-pending.json` and runs `msiexec /i <file> /qn /norestart` (log next to the file). The version running after the installer (the new one, or the old one after a rollback) reports `{commandId,version,succeeded,detail}` as the heartbeat's `upgrade` until a heartbeat carrying it is accepted: success when it runs that version, failure with the installer's status from its log, or failure after an hour without one; the server records the first report per command (audited `UpgradeSucceeded`/`UpgradeFailed`). Only the installed Windows service upgrades; a failed download is retried at the next check.

Signing key rotation (Publisher): GET `/api/settings/signing-key` -> `{keyId,rotation}`; `rotation` is null or `{nextKeyId,startedAt,devices,ready,waiting:[{id,hostName,lastHeartbeat}]}`, `waiting` listing up to 100 devices whose client does not trust the next key yet. POST `/api/settings/signing-key/rotation` creates the next key at `<SigningKeyPath>.next` (409 if one exists). While it exists, every heartbeat reply carries `keyRotation` (`SignedKeyRotation`: `{newPublicKeyPem,newKeyId,issuedAt}` signed with the current key over `"compliance-key-rotation\n" + payload`); clients verify it with the key they pinned, keep the next key, and report both ids in the heartbeat's `policyKeyIds`. POST `/api/settings/signing-key/rotation/complete` `{force?}` re-signs every stored release (same payload) and client package with the next key, keeps the old key as `<SigningKeyPath>.retired-<time>` and signs with the new one from then on; it is 409 while some device does not trust the next key, unless `force` (those devices must enroll again). A client accepts a policy or package signed by either key and makes the next key its only one once a policy signed with it verifies. DELETE `/api/settings/signing-key/rotation` deletes the next key. A completion whose transaction fails puts the old key back; if the server stops in between, startup restores the newest retired key when the stored releases need it. Clients before key rotation report no `policyKeyIds` and never learn the next key, so they count as not ready.

Agent endpoints use Core contracts: unauthenticated POST `/api/agent/enroll` EnrollmentRequest -> EnrollmentResponse; then POST heartbeat HeartbeatRequest -> `{ok,gzipUploads,lastSequence,serverVersion,minimumAgentVersion}`; the request's optional `health` (`{started,queued,oldestQueued,lastUpload,refused,dropped,enforcementError,enforcementErrorAt}`) keeps one `Health` alert per device (`client-health:<id>`) active while it shows a problem (100 or more events waiting for over 30 minutes, events refused in the last day, checks dropped, an error ending programs in the last 10 minutes) and resolves it when none remains, GET policy SignedPolicy, POST events EventBatch -> EventReceipt, GET commands DeviceCommand[], POST `/api/agent/commands/{id}/ack` CommandReply. Compatibility between server and client releases follows `docs/compatibility.md`: devices whose client is older than `minimumAgentVersion` are still served but shown as unsupported (`agentUnsupported`). Signed headers X-Device-Id, X-Timestamp (Unix seconds), X-Nonce (UUID), X-Signature. Canonical signature uses exact body bytes, method uppercase and path without query (Core RequestAuthentication); 5-minute clock window; nonces persisted. Enrollment uses one-time expiring code and distinct ECDSA public key.

Event types `Snapshot`, `Violation`, `Recovered`, `Health`, `BlockedAttempt`, `Tamper`, `Shutdown`, `UsbConnected`, `UsbRemoved`, `UsbBlocked` use persistent sequence >0, immutable event id, source time, object key; Snapshot includes snapshot. Violation/Recovered current incidents advance only on higher sequence per object. Snapshot current selection uses original collection time (and sequence for ties), never arrival time. Source times over 5 minutes in the future are rejected. Event ids and sequences must never be reused with different content. Offline uses server receipt of authenticated heartbeat: SuspectedOffline 3 minutes, Offline 5 minutes. A `Shutdown` event (Windows shutting down) records its receipt time; until the next heartbeat the device is `Shutdown` and gets no offline alert. `Tamper` events open alerts like `Health` (stops, start-up changes, killed runs, refused and completed uninstalls). USB storage events carry object key `usb:<instance id>` and a readable detail; all three are kept in `usb_events` (migration 22, 365 days) and `UsbBlocked` also opens an alert. Readers: GET `/api/usb-events?days=30&deviceId=` (1..365, newest 1000; without `deviceId`, devices in use) -> `[{deviceId,hostName,note,group,at,type,instanceId,detail}]`; GET `/api/usb-events/export.csv` (`ExportUsbEvents`). Policy `usb: {storage: Allow|ReadOnly|Block, allowedDevices: [{id, note}]}` (at most 500, ids 4–200 characters, unique ignoring case); enforce mode with control `usb` needs `storage` other than `Allow`. `ExceptionRequest` events carry object key `exception:<kind>:<target>` and a JSON detail `{kind: Product|Usb, target, label, reason (1..300), days (1..90), user}`; a valid one is kept as a pending request in `policy_exceptions` (migration 23; asked again while pending, the same row is updated) and opens an alert whose summary says who asked for what and why; an invalid one is accepted and ignored. Readers: GET `/api/exceptions` (pending first, newest 1000) -> `[{id,deviceId,hostName,note,group,kind,target,label,reason,days,requestedBy,requestedAt,status: Pending|Approved|Rejected|Revoked,decidedBy,decidedAt,expiresAt,decisionNote}]`. Publishers: POST `/api/exceptions/{id}/approve` `{days?, note?}` (expires `days` after approval), `/reject` `{note?}`, `/revoke` `{note?}` (only an approved exception not yet expired; 409 otherwise), POST `/api/exceptions` `{deviceId, kind, target, label?, reason, days}` (approved at once; a product must be in some policy). Each decision resolves the request's alert and re-issues every policy whose `exceptions` differ from those in force: `[{id, deviceId, kind, target, expiresAt, label, grantedAt}]`, of all devices, at most 2000, same version with a new serial; publishing always replaces the submitted `exceptions`. Maintenance re-issues hourly to drop expired ones. Current verdict UNKNOWN when offline; last verdict remains visible. Historical stale snapshots cannot claim fresh PASS.

Readers: GET `/api/reports/compliance?from=yyyy-MM-dd&to=yyyy-MM-dd&offset=<minutes east of UTC>` (both days included; default the last 7 days; `from` ≤ `to` ≤ today, at most 366 days, `from` within the last 400 days; 400 otherwise) -> `{from, to, generatedAt, start, end: {devices, pass, fail, unknown}, days: [{date, pass, fail, unknown}], groups: [{group, devices, pass, fail, unknown}] (current groups, least compliant first), issues: [{type, subject, devices, alerts}] (alerts of the types Violation, SensitiveFile, Baseline, Tamper, Health, BlockedAttempt, UsbBlocked open at any time in the period, top 20), alertTypes: [{type, opened, devices}] (alerts opened in the period), lingering: [{deviceId, hostName, note, group, since, violationCount}] (devices failing now, longest first, at most 100)}`; verdicts per day follow the overview trend and archived devices are left out. GET `/api/reports/compliance.md` with the same parameters returns the report as Markdown and audits `ExportReport`. `PUT /api/settings/notifications` takes `reportSchedule: Off|Weekly|Monthly` (left out keeps the saved value; with a schedule, `types` may be empty): when enabled, each Monday (Weekly) or 1st (Monthly) from 09:00 for a day, in the server's time zone, the previous week's or month's summary with a link to `<consoleUrl>/reports?from=&to=` is sent once to the configured robot; the period sent is kept in the `report-pushed` setting.

Production uses PostgreSQL and HTTPS. Explicit `Compliance:DemoMode=true`, `Compliance:Storage=Sqlite` requires loopback requests/listener; HTTP permitted only there. Forwarded headers require configured trusted proxy IP(s); never trust arbitrary X-Forwarded-Proto. Deployment configuration details follow in README/deploy documentation.

## Configuration and deployment boundary

- Environment variables map using `__`: `Compliance__Storage=Postgres`, `Compliance__Database=<Npgsql connection string>`, `Compliance__SigningKeyPath=/protected/policy-signing.pem`, `Compliance__BootstrapUsers=<JSON array>`. Use protected secret injection, not command-line passwords. Bootstrap creates absent accounts only; existing passwords/roles are never overwritten. Passwords require at least 16 characters and PBKDF2-SHA256 salts. An empty bootstrap leaves no login account; no default secret exists.
- First startup creates a P-256 signing PEM in the configured path (owner-only Unix mode); retain and back up this key alongside the database. A key inconsistent with stored releases rejects startup. On Windows deployment, the service account directory ACL must protect this key. One server signing identity per customer instance, replaced by key rotation (below) without enrolling devices again.
- Explicit demo: `Compliance__DemoMode=true`, `Compliance__Storage=Sqlite`, `Compliance__Database=/local/data/compliance.db`, `ASPNETCORE_URLS=http://127.0.0.1:5080`. By default both listener and request source must be loopback. For isolated LAN trials only, set `Compliance__DemoHttpLan=true` and bind `ASPNETCORE_URLS` to an explicit private IPv4 address; private IPv4 client sources are then accepted. HTTP carries credentials and reports in cleartext. Do not expose the trial listener to public networks or treat this as production deployment.
- Production requires HTTPS on every request. Terminating TLS at a customer reverse proxy is supported only with `Compliance__TrustedProxies__0=<exact proxy IP>` and subsequent numbered entries. Forward limit is one hop; unknown proxies cannot assert HTTPS through a header. Configure the reverse proxy to replace forwarded headers, limit uploads to 2 MiB (except `POST /api/client-packages`, which takes a client installer of up to 512 MiB), and restrict the application listener to the proxy; deploy PostgreSQL access using a service-specific account and verified TLS. No public CORS is enabled.
- `Reader` must be included for management read access; permission to edit does not implicitly add read permission. Policy publishing is a single Publisher action, recorded in the audit log.
- Build UI before server publish. `ui/dist` is copied to the dev server's ignored `wwwroot` and included as `wwwroot` content in the published output. Static client assets use only same-origin API; login/write requests must preserve cookies and CSRF header.

## Persistence and operational limitations

State lives in typed tables created by ordered migrations in `src/Compliance.Server/Storage/Migrations.cs` (`schema_migrations` records applied versions; startup applies missing ones in one transaction under an advisory lock). Tables: `users`, `sessions`, `enrollment_codes`, `devices`, `events` (primary key `(device_id,event_id)`, unique `(device_id,sequence)`), `alerts`, `snapshot_incidents`, `policy_releases` (immutable; the current policy is the newest release), `policy_drafts`, `commands`, `audit`, `nonces`, `verdict_history`. Each device row also stores its verdict as last evaluated (`verdict`, `violation_count`, `verdict_valid_until`, `verdict_sequence`, `verdict_policy`, `verdict_detail`): written when a snapshot arrives and by a background refresh every 15 seconds for devices whose snapshot, policy or validity no longer matches it; lists read it and only evaluate, without storing, devices whose stored verdict no longer holds. Every change of a stored verdict adds a `verdict_history` row; rows older than 400 days are pruned except each device's latest. Times are stored as UTC ticks (BIGINT); only free-form documents (snapshots, controls, policy payloads, sanitized event bodies) are JSON text. A 0.1.0 database is imported once from `records(kind,id,json)`, which is then kept as `records_legacy_v0` for inspection or rollback. PostgreSQL transactions run concurrently and serialize only where they share state through transaction-scoped advisory locks: per device (heartbeat, event batches, command replies, alert acknowledgment), policy review/publishing, enrollment redemption, offline-state transitions and migrations. SQLite uses a file-backed transaction plus single-process serialization; do not run multiple demo processes on the same file. Events retain original source times and a separate server receipt time; SHA-256 fingerprints allow immutable raw-input deduplication while snapshots, summaries and event payloads are sanitized before persistence. No raw request body, enrollment token or password is recorded in audit.

Device policy assignments reference immutable release versions. A targeted release does not change other devices' assignment. Snapshot-derived incidents aggregate by product and SID (proxy objects remain distinct); direct event incidents update by object key and persistent sequence. Only newest non-stale snapshot state can open/resolve snapshot incidents. Sensitive file evidence (`kind:SensitiveFile`, module `sensitive-files`, scopes are user SIDs or `drive:<letter>`) opens one alert per reported path: type `SensitiveFile` for rules with `action:"Alert"` (the default; no effect on the verdict) and `Violation` for `action:"Violation"`. Such an alert resolves only when a fresh `Complete` scan of its scope no longer lists the path, or when scanning is disabled; `Truncated` or failed scans prove nothing. Baseline evidence (`kind:Baseline`, module `baseline:<check>`, `productId` is the check id) opens one alert per object key: type `Baseline` for rules with `action:"Alert"` and `Violation` for `action:"Violation"`; it resolves when a fresh `Complete` run of that check after the alert no longer reports it, or when the check is disabled. Problems of alert-only checks are listed in the report's `baselineNotes` and never affect the verdict. Recovery requires no coverage gaps and fresh Complete modules for the incident's original scope; it does not follow acknowledgment. Offline transition polling runs every 15 seconds in the background; device and alert reads do not write. Authenticated heartbeat source time must be within five minutes; receipt time determines reachability, never scan freshness.

This build records notifications in the management alert center only; SMTP/external delivery, retention pruning, account administration/password resets, directory identity, policy rollback orchestration and backup/PITR automation remain deployment follow-up work. Preserve database and signing-key backups; perform a real restore test before production rollout. Capacity/load goals have not been measured. Application and browser policy publishing is capability-gated; the generic network adapter is absent and its requested enforcement release is always rejected. No endpoint runs a remote shell, uninstall or arbitrary update payload.

## Verification

`dotnet test tests/Compliance.Server.Tests` uses real durable SQLite files and ASP.NET TestServer. Set `COMPLIANCE_TEST_POSTGRES` to a loopback test-database connection string to run the same suite on PostgreSQL; tests create generated isolated schemas and drop only their own schemas. Tests cover enrollment expiry/reuse/restart, authenticated nonce replay and signature path/body binding, atomic batch rollback, duplicate and sequence conflict handling, out-of-order recovery, old scan freshness, offline current reports, RBAC/CSRF, separate review and immutable publishing, per-device policy targeting, sanitization, snapshot alert recovery and scoped fixed commands. Actual proxy TLS and native Windows controls require separate deployment acceptance.
